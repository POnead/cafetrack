1. Project Overview

Project Title

CafeTrack: Real-Time Stock Monitoring with Barcode-based Authentication for Merrylane Cafe Foodhub

Project Description

CafeTrack is a connected inventory management system designed to automate and streamline the management of ingredient stocks, item checkout, restock operations, and expiration tracking for Merrylane Cafe Foodhub. It provides a centralized, secure, and real-time platform for recording stock movements, generating barcodes, calculating inventory levels, producing reports, and ensuring accountability through an immutable audit trail.

The system reduces manual effort, minimizes human error, and enhances transparency for both staff and administrators. Through Barcode-based authentication and real-time stock deduction, CafeTrack enables the cafe to maintain accurate inventory records while preventing spoilage, waste, and stock discrepancies.

2. Project Goals and Objectives

Primary Objective

To develop a connected inventory management system that allows administrators to manually encode and generate barcodes for ingredients, while enabling staff to perform quick, Barcode-based checkout and real-time stock deduction for Merrylane Cafe Foodhub.

Additional Objectives

Beyond the core client requirements, the system includes the following strategic enhancements to improve usability, accountability, and operational effectiveness:

  • Role-Based Access Control (RBAC): Distinct permissions for Admins (owner/manager) who manage the system, and Staff (cooks/baristas) who can only perform checkout and restock operations.
  • Barcode Authentication (Staff Login): Staff scan their personal barcode codes to log in and enter a password to verify their identity before performing any inventory transactions.
  • Manual Item Management (Admin Check-In): Admins can manually add, edit, or delete ingredients through the web dashboard, inputting details such as category, physical form (liquid/powder), quantity, and expiration dates.
  • Automatic barcode Generation: The system automatically generates unique barcodes or barcodes for each ingredient upon manual entry, which can be printed and affixed to storage containers.
  • Barcode-based Item Checkout/Restock: Staff can scan item barcodes using connected scanner devices to quickly and accurately deduct items from inventory.
  • Multi-Item Checkout with Confirmation: Staff can scan multiple items in one transaction, with a final confirmation step (password/code) required to prevent accidental deductions.
  • Real-Time Stock Updates: Inventory levels automatically adjust instantly in the database and reflect on the admin dashboard immediately after every checkout transaction.
  • Automated Alerts & Reports: The system generates real-time alerts for low-stock levels and near-expiry items, plus historical reports for inventory usage and waste tracking.
  • Immutable Audit Trail: A secure, uneditable chronological log records all system activities (item additions, checkouts, adjustments) with staff identification and timestamps for compliance and accountability.
  • Expiration & Out-of-Stock Alert: The system alerts admin users about items that are near expiration, out of stock, or already expired.

4. Design and Development

User Interface (UI) Design

The CafeTrack system features a clean, modern interface designed for both administrative and staff users. The UI follows a dashboard-based layout with role-specific navigation.

Planned Screens

  1. Login Page — barcode scan input field with password verification for staff; username/password form for admin.
  2. Admin Dashboard — Overview of current stock levels, low-stock alerts, near-expiry alerts, and recent transactions.
  3. Item Management Page — Add/edit/delete ingredients with fields for category, physical form, quantity, and expiration date; barcode generation and print functionality.
  4. Checkout/Restock Page — barcode scanner input, multi-item scan list, and final confirmation button. Three movement modes: Checkout (deduct used stock), Restock (add received stock), and Log Waste (deduct spoiled, spilled, or expired stock). All three require a password confirmation and are recorded with the staff member responsible.
  5. Reports Page — Tab-based interface with usage reports, waste tracking, and export options.
  6. Audit Trail Page — Chronological log with filters for staff, date, and transaction type.
  7. User Management Page — Create/edit/disable user accounts, assign roles, and generate barcode credentials.
  8. Alert Center — Dashboard showing active low-stock, near-expiry, out-of-stock, and expired item alerts with resolution options.

  • Barcode scanning reliability under varied physical conditions — lighting, angle, and distance

  • Verification of TLS 1.3 enforcement in the production hosting environment
  • Compliance with food safety and inventory standards during an operational audit

Known limitations of the security design, stated explicitly:

  • Session invalidation on logout. Sessions are stateless signed tokens, so signing out clears the browser cookie but does not revoke a token that was already issued. A copied cookie remains usable until it expires (15 minutes by default). This is a deliberate trade-off for a low-traffic internal system.
  • Audit immutability is enforced by the application, not the database. No code path exposes a way to edit or delete an audit entry, and the hash chain makes any undetected tampering evident. However, the table itself is not protected by a database-level rule blocking UPDATE or DELETE; a compromised database credential could alter history, which verify_audit_chain() would then detect.
  • Staff can read the full transaction history. Any signed-in staff member may call the transaction history endpoint and see every recorded movement, including those made by other staff. This is a deliberate choice: in a small cafe, visible stock movement supports the transparency and accountability the project goals call for, and reading history is not a system-critical action. It is noted here so the decision is explicit — restricting staff to their own movements would be a straightforward change to the history filter if the client later prefers it.
  • An open alert is not re-typed when the situation worsens. If an item drops below its low-stock threshold and then falls to zero, the existing low-stock alert stays as it is rather than escalating to an out-of-stock alert. The item remains visible on the alert list and is still counted as out of stock on the dashboard, so nothing is hidden; the out-of-stock alert is raised once the earlier one is resolved. Escalating in place would be a small change to the alert-refresh function if the client wants the alert to state the current severity on its own.

7. Implementation Details

Environment Setup

CafeTrack was developed as a web application and runs in a standard Node.js environment. The following tools and technologies are used:

  1. Integrated Development Environment (IDE): Visual Studio Code, used for its integrated TypeScript support, ESLint integration, and Git version control.
  2. Programming Language: TypeScript 5.6, providing static type checking over JavaScript.
  3. Web Framework: Next.js 16.3 (App Router) with React 19, providing server-side rendering, API route handlers, and a build pipeline in one framework.
  4. Database: PostgreSQL via Supabase. A local development mode uses PGlite (PostgreSQL compiled to WebAssembly) so the system runs with no external account or network connection.
  5. Barcode Generation: jsbarcode, rendering Code 128 barcodes as SVG at exact integer module widths for reliable scanner reading and printing.
  6. Styling: Tailwind CSS 3.4 with a custom design system.
  7. Scanner Integration: USB barcode/barcode scanners are supported through standard keyboard-input handling, so no dedicated driver is required.

Libraries and Dependencies

  • next (16.3.6) — web framework, routing, and API route handlers
  • react / react-dom (19.3.0) — user interface
  • jose (5.9.6) — JSON Web Token signing and verification for sessions
  • @supabase/supabase-js (2.45.4) — PostgreSQL access in hosted mode
  • @electric-sql/pglite (0.5.8) — embedded PostgreSQL for local development
  • jsbarcode (3.12.3) — Code 128 barcode and label generation
  • node:crypto — scrypt password hashing, salt generation, and constant-time comparison

Architecture

Business logic is separated across three layers:

  • Presentation layer — React page components under src/app, with shared UI elements in src/components.
  • API layer — Next.js route handlers under src/app/api, each enforcing authentication and role checks before delegating.
  • Data layer — PostgreSQL functions (process_transaction, append_audit, verify_audit_chain, refresh_alerts) that execute stock movements and audit writes atomically, guaranteeing that the audit trail cannot break under concurrent access.

Backup and Restore

The system provides database backup and restore capability through the commands npm run db:backup and npm run db:restore, satisfying SR-N20. Additional maintenance commands are available: npm run db:reset and npm run db:wipe.
